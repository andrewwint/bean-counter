# infra — AWS CDK skeleton

> ## ⚠️ NOT DEPLOYED. NOT REVIEWED FOR PRODUCTION.
>
> **Do not run `cdk deploy` or `cdk bootstrap` against any AWS account without an explicit
> security review and the account owner's approval.**
>
> This directory describes the *shape* the application would need in AWS. It has never been
> deployed, it has never been through a security review, and it provisions resources that
> cost real money the moment they exist. `cdk synth` is the only command that is safe to run
> casually, and it is the only command anyone has run here.

## 💸 The cost warning nobody expects

The surprising thing about this stack is not the compute. It is the two resources that bill
**by the hour, whether or not anybody uses the application** — including overnight, over a
weekend, and for the three weeks after you forgot you deployed it.

| Resource | Why it costs what it costs | Rough order of magnitude |
| --- | --- | --- |
| **NAT gateway** | Billed per hour *plus* per GB processed. Idle traffic still costs the hourly rate. This is the classic surprise line item. | ~$30–35/month, per gateway |
| **RDS instance** | Billed per hour while the instance exists. Stopping it only pauses billing for 7 days, after which AWS starts it again. | ~$12–20/month for `t4g.micro` + storage |
| **Application Load Balancer** | Billed per hour plus per capacity unit. | ~$16–25/month |
| CloudFront + S3 | Usage-based; genuinely near-free at learning traffic levels. | cents |

**A rough total of $60–90/month for a stack serving zero users.** These are order-of-magnitude
figures for a single region and will differ by region and over time — check the
[AWS Pricing Calculator](https://calculator.aws/) for real numbers before you commit to anything.

Two further traps worth naming, because both cost money *after* you think you've cleaned up:

- **The database is `RemovalPolicy.RETAIN`, on purpose.** `cdk destroy` will delete the stack and
  **leave the RDS instance running and billing**. That is the right default — the event log is the
  system of record, and no convenience is worth silently deleting it — but it means cleanup is a
  two-step job. Delete the instance by hand, and check for a retained final snapshot too.
- **`deletionProtection: true`** means the instance also refuses to be deleted until you turn that
  off first.

## What is in the stack

```
Internet ──> CloudFront ──> S3 (private)              the React stock board, static files
         └─> ALB (public subnets)
               └─> Fargate service (private subnets)  the Node API, port 3000
                     └─> RDS Postgres 16 (isolated)   the event log — the system of record
```

Three boundaries, each deliberate:

1. **The database sits in isolated subnets.** No NAT, no internet gateway, no egress. It is
   reachable only from the API's security group, on the database port — not from the VPC CIDR
   and not from a wide-open rule.
2. **The API runs in private subnets.** Inbound traffic arrives only through the load balancer.
3. **The S3 bucket is fully private.** CloudFront reads it through Origin Access Control; the
   bucket policy refuses everything else. Public access is blocked at the bucket level as well.

Credentials are generated by Secrets Manager and injected into the container at runtime. **No
password, account id, or ARN is committed to this repository.** The account and region come from
`CDK_DEFAULT_ACCOUNT` / `CDK_DEFAULT_REGION` in the caller's environment, which is also why a
deploy requires someone to have deliberately configured credentials and bootstrapped an account.

## The deploy gate

`lib/bean-counter-stack.ts` declares a CloudFormation parameter with **no default value** and
exactly one allowed value. `cdk synth` is unaffected, but `cdk deploy` cannot proceed unless
someone explicitly types the acknowledgement:

```
--parameters AcknowledgeNotProductionReady="I have read infra/README.md and had this reviewed"
```

That guardrail is code rather than a paragraph, because a paragraph cannot stop a command. It is a
speed bump against an accident, **not** a security control and not a substitute for the review.

## Running it

```bash
nvm use            # Node 22
npm install
npm run typecheck  # tsc --noEmit
npx cdk synth      # generates cdk.out/ locally — makes no AWS API calls that change anything
```

`cdk synth` is the only command that has been run against this code. `cdk.out/` is gitignored;
the synthesized template embeds whatever region your environment resolves to, which is another
reason not to commit it.

## Known gaps — read before treating this as a starting point

This is a skeleton, and the following are missing on purpose. Each one is a real requirement that a
production deployment would have to answer, and the list is here so nobody mistakes the skeleton
for a design.

- **No TLS on the API.** The load balancer listens on HTTP only, because a certificate needs a
  domain name this project does not have. Production needs ACM plus an HTTPS listener, and the
  HTTP listener should redirect rather than serve.
- **The container image is a placeholder.** It points at a stock `node:22-alpine` from a public
  registry so the stack synthesizes without a Docker build. A real deployment builds `backend/`
  and pushes to ECR.
- **No migration strategy.** Nothing runs `make migrate` against the RDS instance. That needs to be
  a deliberate step (a one-off task or an init container), not something bolted onto container
  startup where two tasks could race each other.
- **No WAF, no rate limiting, no CORS review** for a real origin.
- **No secret rotation.** Secrets Manager can rotate the database credential; this stack does not
  configure it.
- **No alarms, no dashboards, no log retention policy.** Logs will accumulate and bill.
- **Single AZ database, one NAT gateway.** Both are cost choices, not availability choices, and
  both are wrong for production.
- **No backup verification.** Seven days of automated backups are configured; nobody has ever
  tested restoring one, and an untested backup is a hypothesis.

## Layout

```
bin/bean-counter.ts        CDK app entry point; wires the environment from CDK_DEFAULT_* vars
lib/bean-counter-stack.ts  the single stack — VPC, RDS, Fargate + ALB, S3 + CloudFront
cdk.json                   CDK CLI config and feature flags
```

This package is CommonJS, following the CDK project convention, rather than ESM like the rest of
the repo. It is an independent package with its own `node_modules` and is not part of the npm
workspace.
